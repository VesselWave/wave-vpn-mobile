# Staff comment 268266: UI and emulator checks (items 3 and 4)

Source: [AirVPN Staff report, 7 November 2026](https://airvpn.org/forums/topic/82017-wave-vpn-open-source-wireguard-client-for-android-and-linux-unofficial-v011/?do=findComment&comment=268266), items 3 (failed backend start leaves a blocking interface behind a "Disconnected" screen) and 4 ("Only selected" with nothing checked tunnels every app). Checked against v0.1.4 (`72ac16a`) on two API 37 emulators. Protocol and recovery items 1 and 2 are in [FORUM-REGRESSIONS-2026-11-07.md](FORUM-REGRESSIONS-2026-11-07.md).

These checks only detect the defects. No production code was changed and nothing was fixed. No real account, private profile or AirVPN request was involved; all session data was fabricated.

## Result

| Check | emulator-5556 | emulator-5554 |
| --- | --- | --- |
| 4 positive controls (`ForumUiControlsTest`) | pass | pass |
| Item 3: failed start must not hide a blocking interface | **fails: 2 violations** | **fails: 2** |
| Item 4: empty "Only selected" must not route unchecked apps | **fails: 2** | **fails: 2** |
| Item 4: empty "Only selected" must say so on screen | **fails: 1** | **fails: 1** |
| Extra: "Cancel connecting" reachable by accessibility | **fails** | **fails** |

The default run (controls only) exits 0. The contract run exits 1 on both devices, with the same four failures on repeated runs. Run without the opt-in, the contract class reports its tests as skipped, and the runner script never counts a skip as a pass.

Observed evidence, taken from Android's own `dumpsys connectivity` for the qa app's VPN network:

- **Item 3.** After the injected backend UP failure, the VPN is `192.0.2.1/32, fd00:7761:7665::1/128`, MTU 1280: Wave's blocking interface. It routes uids `0-99999`, so Camera and Chrome are routed into a sink. The screen meanwhile shows "Disconnected", "Couldn't connect. Check account, server and WireGuard settings" and a single action: Connect. Tapping Connect fails the same way and the block stays. In the agent-device run on emulator-5554, `ping 1.1.1.1` from the shell was **blocked** throughout, and only killing the qa process released it.
- **Item 4.** With "Only selected" and zero apps checked, the WireGuard interface (`10.128.0.2/32`, MTU 1320) routes uids `0-99999`, Chrome and Camera included. The screen says "Only checked apps use the VPN. Everything else connects directly." and gives no empty-selection notice. The positive controls show that the same harness sees correct per-app routing for Only selected {A}, Bypass {A} and All apps.

## Run it

Use an emulator with no other VPN active. The script refuses to run if another app owns a VPN, because the qa tunnel would revoke it.

```sh
# Positive controls only; must exit 0.
python3 scripts/forum-ui-emulator.py --serial emulator-5556
# Controls plus desired-behavior contracts; exits 1 while items 3/4 are unfixed.
python3 scripts/forum-ui-emulator.py --serial emulator-5556 --contracts
```

Exit codes:
- 0: everything that ran passed.
- 1: a contract failed (a defect was reproduced).
- 2: a control or the harness failed, or a check was skipped or missing; contract results then mean nothing.
- 3: setup was refused.

Output goes to `build/forum-ui/`: `report.json`, the raw `instrumentation.txt`, and `forum-ui/*.png|txt`. The report also records source revision, working-tree status, APK hashes and Android API level. Missing or duplicate test results and absent final instrumentation completion fail qualification. Each text record holds the app state, the VPN snapshot, on-screen text and the accessibility tree.

The equivalent Gradle command is `ANDROID_SERIAL=emulator-5556 ./gradlew :app:connectedQaAndroidTest -Pandroid.testInstrumentationRunnerArguments.waveForumContracts=1`. Without `ANDROID_SERIAL`, Gradle runs on every connected device. A full run takes about 1–2 minutes.

## How the harness works

- **Isolated build.** A `qa` build type (`me.vwave.vpn.qa`) and `testBuildType = "qa"`. Instrumented tests therefore cannot install over or seed the signed-in `me.vwave.vpn.dev` or release apps, and `ForumQaRunner` refuses any other package. AGP 9 would otherwise drop debug JVM tests, so `androidComponents` keeps `:app:testDebugUnitTest` enabled for debug only.
- **Synthetic offline session.** Before `WaveApp.onCreate`, `ForumQaRunner` writes a fabricated account to the real encrypted `SessionVault`: random keys, one server, and every address in TEST-NET-1. Both documents are marked fresh, so ordinary refreshes send nothing. The real repository, `TunnelManager`, GoBackend and Compose UI run unchanged.
- **Real UI, real OS oracle.**
  - Tests launch `MainActivity` and drive it through the accessibility tree. The Compose test rule never goes idle while the Connecting spinner animates.
  - A real touch is used only where the tree hides a control (see the extra finding).
  - Routing claims are checked against Android's per-uid VPN ranges and link addresses, not against app state.
- **Fault injection without production hooks.** The account's second device has DNS `0.0.0.0`. It passes Wave's and WireGuard's config validation, but `VpnService.Builder.addDnsServer` rejects it inside `GoBackend.setState(UP)`, after Wave has installed its blocking interface. That is the code path in item 3.
- **Safety guards.**
  - After an unanswered handshake, the next connect would send the synthetic login to AirVPN's real fallback bootstrap. Every tunnel test therefore cancels before the 10 s handshake deadline, and `assertNoRecoveryPending` aborts the run if recovery was ever armed. During development it did abort two runs, which is how the 8 s wait limit was chosen.
  - Teardown uses the app's own disconnect path and verifies that no VPN remains; a cleanup timeout fails the run.
- **Positive controls before contracts.** Each contract first asserts that its injection actually happened ("Unable to start WireGuard" after "Connecting to Qa-Synthetic"). A harness problem therefore cannot pass as a defect, or the reverse.

## Extra findings while building the checks

1. **"Cancel connecting" is invisible to accessibility services** (contract `busyCancelIsExposedToAccessibility`, fails). While Connecting, the 196 dp `CircularProgressIndicator` fully covers the 176 dp power button. Compose drops fully covered nodes from the accessibility tree, so TalkBack and Switch Access users cannot cancel. A finger tap still works.
2. **An uninstalled "Only selected" app does not fail on API 37.** I first tried that injection for item 3. Android accepted the unknown package and established a VPN with an empty uid set (`Uids: <{}>`), which routes nothing. On older Android, `addAllowedApplication` throws `NameNotFoundException`. If so, uninstalling a selected app is a realistic field trigger for item 3, but this was not tested on a pre-37 image.
3. **dumpsys caveat.** When the blocking interface and the WireGuard interface share the same app set, Android updates the VPN agent in place and keeps the old `sessionId` ("Wave — blocking traffic"). The harness therefore identifies the interface by its addresses and MTU, never by session name.

## Why these were missed (UI side)

1. **UI state was never checked against the OS.** The Overview derives its chip and action from `TunnelState` alone. `Failed` maps to "Disconnected" and Connect whatever `WaveVpnService.isBlocking` says. No check compared what the screen claims with what Android routes, even though the status-bar key icon shows the contradiction immediately.
2. **The failure branch was never injected.** Earlier runtime QA injected network faults (UDP drops, unusable cellular), and `STAFF-INFRA-EMULATOR-2026-11-05.md` says the failed-recovery branch was not fault-injected. Without an injectable backend failure and an isolated session, an agent working on the signed-in app had good reason not to risk its credentials or leave the emulator blocked.
3. **Split tunneling was only tested on the happy path.** Checks used one or more selected apps. `wgQuickConfig` silently omits `IncludedApplications` for the empty set, and the copy describes the non-empty case.
4. **No instrumented tests existed, and CI did not run app JVM tests.** Nothing executed the UI against a real `VpnService`. This change adds `:app:testDebugUnitTest` to CI and CONTRIBUTING. The emulator suite stays a local and agent command, because hosted CI has no KVM emulator.

## UI recommendations (not implemented)

- **Item 3.** Treat "blocking interface present" as its own visible state, never as "Disconnected":
  - an amber "Blocking traffic" chip;
  - copy saying apps have no internet until Wave connects or you stop blocking;
  - a primary **Stop blocking** (disconnect) action next to **Try again**.

  When Android lockdown is on, explain that Android keeps blocking, and link to Always-on VPN instead. Derive the chip from `isBlocking`, not only from `TunnelState`. Replace the generic "Check account, server and WireGuard settings" with the failing step.
- **Item 4.** With zero apps checked under Only selected:
  - show an inline warning ("No apps selected — Connect will …");
  - make the Settings row read "Only selected · none" with warning styling;
  - have Connect refuse with that message, or route nothing, whichever behavior is chosen.

  The behavior and the copy must agree. The routing contract accepts either outcome.
- **Accessibility.** Apply `clearAndSetSemantics {}` to the decorative spinner, or draw it inside the button. Put `stateDescription = "Connecting"` on the button so "Cancel connecting" stays reachable.

## Recommended agent QA loops

1. **Claim versus reality.** For every visible state and promise in the copy, name an OS oracle: VPN uid ranges, link addresses, reachability from the shell uid, or the status-bar key icon. Fail when they disagree. That single rule would have caught items 3 and 4.
2. **Every catch branch gets an injection.** List each `catch` and `throw` in `vpn/` and `data/`. Each needs a test that reaches it through synthetic data (like the 0.0.0.0 DNS device) rather than production test hooks. Track uncovered branches in the report.
3. **Boundary sweep for every setting.** Cover empty, one, all, and invalid or uninstalled values. Run it whenever a settings model changes.
4. **Red before green.** Each staff or forum item becomes an opt-in contract that fails on the current build. The fix change removes the opt-in and keeps the test. Never invert a contract into a passing "expected broken" test.
5. **Isolated, destructive-safe environment.** Agents run against the `qa` app and synthetic session, with no-network guards and verified teardown. They never use the signed-in app for failure paths. They refuse to start if another VPN is active, and they release device sessions when done: during this run another thread held emulator-5556's agent-device session, so UI evidence there came from in-process instrumentation.
6. **Accessibility audit for every state.** In each tunnel state, every visible action must have a labelled, clickable accessibility node. This check found the hidden cancel action.
7. **Cadence.** On any change under `vpn/` or `ui/`:
   - run `forum-ui-emulator.py` (controls must exit 0);
   - diff the contract `report.json` against the previous run;
   - attach the evidence PNGs to the review.

   Before a release, repeat on several API levels (26, 30, 34, 37), since platform behavior differs (see finding 2).

## Gaps

- Only API 37 Google emulator images. No physical, OEM, pre-37 or Android-lockdown run, and lockdown changes item 3's correct behavior.
- The item 3 injection is synthetic (invalid DNS), not any specific failure a user has hit. Real triggers include `establish()` returning null or a revoked consent. They take the same `catch` path but were not separately injected.
- The text contract for item 4 matches a set of notice phrases. Whoever fixes it may need to update the regex for the final wording. The routing contract does not depend on copy.
- The checks need an emulator and are not in hosted CI.
